## 发现的冲突

三方合并实际检测到 README.md、app.js、styles.css、server.rb 四个文件冲突。主干已包含首页独立更新、冰箱 AI/拍照/手动录入和个人资料页；菜谱分支仍带有早期同名页面、全局事件及通用 CSS，直接覆盖会使主干新增功能消失。同名 `today` 在两边分别是字符串和函数，直接拼接也不安全。

## 保留范围与接入方式

- `app.js`、`styles.css` 与核对的主干逐字一致；原首页、冰箱、我的与采购页面、事件和布局保留。主干知识库、构建脚本、seed.json、首页图片均保留。
- `recipe.html` 使用独立文档、`recipe-app.js` 和 `recipe-styles.css` 承载已有菜谱体验。由同源 iframe 隔离样式、同名变量及 document 级事件，避免影响原三个页面。它不使用第二份库存或第二份用户偏好。
- 主页面只额外加载 `recipe-host.js/css`：将“吃什么”接入原导航，支持 `#home/#inventory/#recipes/#shopping/#profile`；首页菜卡和“我的”入口进入菜谱详情/发现，返回仍进入原页面。
- 子页面不显示第二套底部导航。离开时等待已有记账写入，然后主页面重新读取服务端状态；返回时刷新共享数据并保留原制作文档。消息同时验证同源、发送窗口和专用 channel。
- 菜谱名称匹配复用主干知识库（如番茄/西红柿），克/g、毫升/ml按同量单位匹配；斤和g等涉及换算的单位仍提示核对，不盲目扣减。前端新鲜度复用主干规则，后端菜谱与记账复核同一份知识库，不会将标记新鲜但按主干已不宜食用的食材继续投入推荐或消耗。
- 后端保留原 `/api/agent`、`/api/ai-inventory`、`/api/photo-inventory`、知识库和首页图片服务，同时接入菜谱、导入、图片及幂等记账接口。共享保存采用锁、原子写入和 revision；陈旧页面保存被拒绝，不覆盖较新的库存。库存确认/撤销仍比较完整快照。
